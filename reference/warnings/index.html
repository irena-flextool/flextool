    Warnings and notes

    A FlexTool run reports a problem it can work around as one console line per kind of problem and solve, ending in a code:

    Warning: <what is wrong> (<N> cases, e.g. '<first entity>') [W-0123]

    The line names how many entities are affected and the first of them; the full list (and the values behind each case) is in the run's log at debug level (run with --debug). At the end of a run a summary counts the warnings of each code. Note: lines are information, not problems.

    This page explains each code: what it means and how to fix it. Its address is https://irena-flextool.github.io/flextool/reference/warnings/, and the section of a code is # followed by the code in lowercase (for example #w-0001). The FlexTool GUI opens it when you click a code in the run output.

    Not every FlexTool warning has a code yet; the lines without one explain themselves.

    Behaviour changes

    W-0600

    Behaviour change: storage_default_fix_nothing (note). Console line:

    Note: changed in <version>: storage starts free by default (fix_nothing) (<N> cases, e.g. '<name>') [W-0600]

    The default storage_start_end_method is now fix_nothing: a storage node without its own storage_start_end_method starts free. Before, when some node had a storage_state_start, it was fixed at the start: at its own storage_state_start, or at 0 when only other nodes had one (results change).

    The notice is printed for a database upgraded from an earlier FlexTool, once per run (the debug log names every affected entity and gives the full notice).

    How to fix: check the results of the affected entities. Set storage_start_end_method on these nodes (fix_nothing keeps the new behaviour).

    W-0601

    Behaviour change: storage_fix_method_rewritten (note). Console line:

    Note: changed in <version>: the upgrade rewrote storage_start_end_method (<N> cases, e.g. '<name>') [W-0601]

    The database upgrade rewrote storage_start_end_method on these nodes, so results are unchanged. A fix_start / fix_end / fix_start_end without storage_state_start / storage_state_end is now an error. The default is now fix_nothing, so a node that used the old default fix_start with its own storage_state_start now has fix_start written.

    The notice is printed for a database upgraded from an earlier FlexTool, once per run (the debug log names every affected entity and gives the full notice).

    How to fix: check the results of the affected entities. Delete the marker flextool_behaviour_change:storage_fix_method_rewritten in the database's Metadata tab once checked.

    W-0602

    Behaviour change: user_constraint_prebuilt_nets_retirements (note). Console line:

    Note: changed in <version>: pre-built capacity term subtracts retirements (<N> cases, e.g. '<name>') [W-0602]

    The pre-built capacity term of a user constraint (constraint_cumulative_pre_built_capacity_coeff) now subtracts the capacity retired in earlier periods of the same solve too (before: only retirements of earlier solves of a chain), so a single solve and a chain of solves agree.

    The notice is printed for a database upgraded from an earlier FlexTool, once per run (the debug log names every affected entity and gives the full notice).

    How to fix: check the results of the affected entities. Delete the marker flextool_behaviour_change:user_constraint_prebuilt_nets_retirements in the database's Metadata tab once checked.

    W-0603

    Behaviour change: dc_power_flow_lines_beside_dc_links (note). Console line:

    Note: changed in <version>: DC power-flow lines are the group's connections (<N> cases, e.g. '<name>') [W-0603]

    DC power-flow lines are the connections inside dc_power_flow_with_angles groups (other than is_DC connections). Before, a model with any is_DC connection used the is_DC connections instead: the group's lines had no angle constraints and the reference node could move (results change).

    The notice is printed for a database upgraded from an earlier FlexTool, once per run (the debug log names every affected entity and gives the full notice).

    How to fix: check the results of the affected entities. Delete the marker flextool_behaviour_change:dc_power_flow_lines_beside_dc_links in the database's Metadata tab once checked.

    W-0604

    Behaviour change: ladder_tier_labels_as_written (note). Console line:

    Note: changed in <version>: price-ladder tier labels are kept as written (<N> cases, e.g. '<name>') [W-0604]

    Price-ladder tier labels are now kept as written: tiers such as 01 or a are their own tiers. Before, a label was read as a whole number, so 01 became 1 (such tiers were bought at no cost, and 1 and 01 were merged) and tiers like a were dropped (results change).

    The notice is printed for a database upgraded from an earlier FlexTool, once per run (the debug log names every affected entity and gives the full notice).

    How to fix: check the results of the affected entities. Delete the marker flextool_behaviour_change:ladder_tier_labels_as_written in the database's Metadata tab once checked.

    W-0605

    Behaviour change: unnamed_maps_read_per_depth (note). Console line:

    Note: changed in <version>: maps without index names are read per depth (<N> cases, e.g. '<name>') [W-0605]

    Maps without index names that have different depths within one parameter are now read per depth: a one-level map keyed by time steps next to a period x time map is read over time. Before, its time steps were read as periods and its values were lost (results change).

    The notice is printed for a database upgraded from an earlier FlexTool, once per run (the debug log names every affected entity and gives the full notice).

    How to fix: check the results of the affected entities. Delete the marker flextool_behaviour_change:unnamed_maps_read_per_depth in the database's Metadata tab once checked.

    W-0606

    Behaviour change: price_ladder_periods_from_solve_periods (note). Console line:

    Note: changed in <version>: a ladder without periods applies in every period (<N> cases, e.g. '<name>') [W-0606]

    A price_ladder_annual given without periods now applies in every period of a solve that has no period_timeset (the model's only timeset is used). Before, when the model had no periods_available either, the ladder was skipped with a warning (results change).

    The notice is printed for a database upgraded from an earlier FlexTool, once per run (the debug log names every affected entity and gives the full notice).

    How to fix: check the results of the affected entities. Delete the marker flextool_behaviour_change:price_ladder_periods_from_solve_periods in the database's Metadata tab once checked.

    W-0607

    Behaviour change: coarse_process_flows (note). Console line:

    Note: changed in <version>: processes of coarse nodes have coarse flows (<N> cases, e.g. '<name>') [W-0607]

    A unit or connection whose balance nodes are all in coarse new_stepduration groups now has one flow per coarse step of its nodes (before: one per time step of the solve), with its availability, profiles and efficiency averaged over the coarse step and its ramp limits between coarse steps; a unit with online variables decides its units online, start-ups and shut-downs once per coarse step, counts its minimum up / down time in whole coarse steps and takes its start-up / shut-down capacity reduction over the coarse step; a reserve provider holds one reserve per coarse step, the requirement checked at every time step; an exact connection chooses its direction and the nodes of a DC network whose lines are all coarse their angle once per coarse step; a capacity-margin, inertia, non-synchronous, flow-group instant-flow, user-constraint, storage-use tie or DC power-flow row whose units and connections are all coarse is averaged over the coarse step, and one that mixes them with units at the solve's step sees the coarse flows constant (results change where, within a coarse step, a cost, price, efficiency, minimum load, demand, inflow, profile or row limit varies, two or more limits vary, ramp limits apply, the unit has online variables or provides reserves, or a row mixes coarse and solve-step flows).

    The notice is printed for a database upgraded from an earlier FlexTool, once per run (the debug log names every affected entity and gives the full notice).

    How to fix: check the results of the affected entities. Delete the marker flextool_behaviour_change:coarse_process_flows in the database's Metadata tab once checked.

    W-0608

    Behaviour change: construction_lead_time_commissioning (note). Console line:

    Note: changed in <version>: lead-time capacity counts when it comes online (<N> cases, e.g. '<name>') [W-0608]

    With a construction lead time, 'invested' and the per-period investment limits count capacity coming online in the period; annuity and fixed cost are paid only while it operates, at the invest_cost of the period it comes online; the start of operation uses the whole model's periods; investments starting after the solve or model horizon are not offered (results change).

    The notice is printed for a database upgraded from an earlier FlexTool, once per run (the debug log names every affected entity and gives the full notice).

    How to fix: check the results of the affected entities. Delete the marker flextool_behaviour_change:construction_lead_time_commissioning in the database's Metadata tab once checked.

    W-0609

    Behaviour change: chained_solve_costs_from_run_start (note). Console line:

    Note: changed in <version>: costs of a run of solves count from its start (<N> cases, e.g. '<name>') [W-0609]

    In a run of several solves the reported costs are now discounted from the start of the run (before: from the start of each solve); the investment and fixed cost of new capacity cover its operating years in the whole run and are reported once, in the period it starts operating, by the solve that realizes that period (before: in the decision period, over the deciding solve's periods); the fixed cost of capacity carried from an earlier solve or retired is no longer charged again as existing capacity. The printed objectives stayed discounted from each solve's start until chained_solve_discount_from_run_start (results change).

    The notice is printed for a database upgraded from an earlier FlexTool, once per run (the debug log names every affected entity and gives the full notice).

    How to fix: check the results of the affected entities. Delete the marker flextool_behaviour_change:chained_solve_costs_from_run_start in the database's Metadata tab once checked.

    W-0610

    Behaviour change: stochastic_branch_period_years (note). Console line:

    Note: changed in <version>: stochastic branch periods count from their year (<N> cases, e.g. '<name>') [W-0610]

    In a stochastic solve whose investments do not branch per forecast (stochastic_invest_method none, invest_solve_branching_method operations_only from FlexTool 4.7.0 on), the branch periods of the stochastic branches now count from the year of their period. Before, every branch period counted as the first year of the solve: capacity invested in a later period, or starting to operate in a later period after a construction lead time, was missing from the branches of that period, and lifetimes ended late in the branches (results change).

    The notice is printed for a database upgraded from an earlier FlexTool, once per run (the debug log names every affected entity and gives the full notice).

    How to fix: check the results of the affected entities. Delete the marker flextool_behaviour_change:stochastic_branch_period_years in the database's Metadata tab once checked.

    W-0611

    Behaviour change: ramp_branch_point_shutdown_once (note). Console line:

    Note: changed in <version>: branch-point ramp counts the shut-down once (<N> cases, e.g. '<name>') [W-0611]

    At a stochastic branch point (a step continued by several mid-horizon branches) the downward ramp row of each branch's first step now counts the shut-down share of the units online at the branch point once. Before, it was multiplied by the number of branches squared, so units shutting down there could drop their flow faster than the ramp limit allows (results change).

    The notice is printed for a database upgraded from an earlier FlexTool, once per run (the debug log names every affected entity and gives the full notice).

    How to fix: check the results of the affected entities. Delete the marker flextool_behaviour_change:ramp_branch_point_shutdown_once in the database's Metadata tab once checked.

    W-0612

    Behaviour change: retirement_of_existing_capacity_only (note). Console line:

    Note: changed in <version>: only existing capacity can be retired (<N> cases, e.g. '<name>') [W-0612]

    Only capacity that existed before the run can be retired, and a retirement counts until that capacity's end of life (reinvest_choice / no_reinvestment: the run's first year plus lifetime_technical, in every solve of a chain and once with stochastic branches in the first period; before, a later solve counted it from its own first period and branches multiplied it; reinvest_automatic: the end of the run). It saves each period's fixed cost of the existing capacity in that window, with the factor that fixed cost is charged with (its net salvage value is unchanged: an annuity over payback_time). Periods without existing capacity have no retirement option. Before, a retirement counted in every later period (past the end of life the capacity went negative: an infeasible or zero retirement), chained solves subtracted it from every period, and its fixed-cost saving was counted over the technical lifetime from the retirement (results change).

    The notice is printed for a database upgraded from an earlier FlexTool, once per run (the debug log names every affected entity and gives the full notice).

    How to fix: check the results of the affected entities. Delete the marker flextool_behaviour_change:retirement_of_existing_capacity_only in the database's Metadata tab once checked.

    W-0613

    Behaviour change: acceptance_ceiling_follows_tolerance (note). Console line:

    Note: changed in <version>: near-optimal acceptance follows the tolerance (<N> cases, e.g. '<name>') [W-0613]

    A solve HiGHS could not certify as optimal (status Unknown) is now accepted as near-optimal when its largest relative primal infeasibility is within max(1e-6, 10 x its primal_feasibility_tolerance), and its primal-dual objective error is within the accepted gap. Before, the limit was 1e-6 whatever the tolerance, so a solve run with a looser tolerance (e.g. 1e-3) stopped the run without results; it now writes results.

    The notice is printed for a database upgraded from an earlier FlexTool, once per run (the debug log names every affected entity and gives the full notice).

    How to fix: check the results of the affected entities. Delete the marker flextool_behaviour_change:acceptance_ceiling_follows_tolerance in the database's Metadata tab once checked.

    W-0614

    Behaviour change: solve_step_series_combined (note). Console line:

    Note: changed in <version>: new_stepduration combines series by their kind (<N> cases, e.g. '<name>') [W-0614]

    A solve with new_stepduration now combines every time series over the time steps of each new step by the kind of its value: prices, costs, limits, availability, min_load, penalties, reservations, self-discharge, time-step weights and profiles take the duration-weighted mean, efficiencies the harmonic mean (exact fuel use at a constant flow), inflow the sum and storage_state_reference_value the value at the end of the step. Before, these took the value of the step's first time step; only time-map profiles and inflow were combined (results change). A stochastic (branch) inflow used to take its first time step's value once; it is now summed like a deterministic inflow, so it grows by the number of time steps each new step combines, also where it is constant within the step.

    The notice is printed for a database upgraded from an earlier FlexTool, once per run (the debug log names every affected entity and gives the full notice).

    How to fix: check the results of the affected entities. Delete the marker flextool_behaviour_change:solve_step_series_combined in the database's Metadata tab once checked.

    W-0615

    Behaviour change: energy_margin_adder_per_original_step (note). Console line:

    Note: changed in <version>: energy_margin_adder is per timeline step (<N> cases, e.g. '<name>') [W-0615]

    energy_margin_adder is now an energy per time step of the timeline: when the investment solve has new_stepduration, a solve step adds the sum of the values of the time steps it combines (a constant or period value counts once per time step). Before, a solve step added the value of its first time step once, so a coarse investment solve added less demand (results change). To keep the old demand, divide the value by the number of time steps a solve step combines.

    The notice is printed for a database upgraded from an earlier FlexTool, once per run (the debug log names every affected entity and gives the full notice).

    How to fix: check the results of the affected entities. Delete the marker flextool_behaviour_change:energy_margin_adder_per_original_step in the database's Metadata tab once checked.

    W-0616

Each of them adds the flow as a band of the node group's dispatch plot, so the plot counts the flow more than once and the dispatch does not balance. The model itself is not affected. The debug log lists the flowGroups of each flow.

    How to fix: keep each flow in one dispatch-plot flowGroup. A flowGroup that is only needed for its standalone indicators can use flow_aggregator: standalone_aggregator_only, which may overlap with others.

    W-0100

    Storage node with demand in a capacity-margin group (warning). Console line:

    Warning: capacity-margin group has storage nodes with demand; not covered (<N> cases, e.g. '<name>') [W-0100]

    A group with capacity_margin_method absolute or relative_of_peak_demand has a storage node with demand (a negative inflow, e.g. a heat node with a tank). The capacity margin covers the demand of the group's nodes without a storage state, so that demand is left out of the margin. The debug log names the nodes.

    How to fix: model the demand on a balance node of the group, connected to the storage node, if the margin should cover it.

    W-0101

    Group limit without its method or flag (warning). Console line:

    Warning: group has <limit> without its method or flag; ignored (<N> cases, e.g. '<name>') [W-0101]

    The capacity margin, inertia and non-synchronous constraints are built only for the groups that switch them on: capacity_margin_absolute needs capacity_margin_method: absolute, capacity_margin_relative needs capacity_margin_method: relative_of_peak_demand, inertia_limit needs has_inertia: yes and non_synchronous_limit needs has_non_synchronous: yes. The group has a non-zero limit without it, so the limit is ignored.

    How to fix: set the method or flag, or remove the limit.

    W-0102

    Group method or flag without its limit (warning). Console line:

    Warning: group has no <limit> for its method or flag (read as 0) (<N> cases, e.g. '<name>') [W-0102]

    The group switches on a capacity margin, inertia or non-synchronous constraint (see W-0101 for the pairs) but has no value for its limit, so the model reads the limit as 0: a capacity margin of 0 (the capacity must cover the demand), no inertia requirement, or no non-synchronous infeed allowed (violations are penalised). An explicit 0 is a deliberate input and is not reported.

    How to fix: give the limit a value, or switch the method or flag off.

    W-0103

    CO2 cap without a capping co2_method (warning). Console line:

    Warning: group has <limit> but its co2_method has no such cap; ignored (<N> cases, e.g. '<name>') [W-0103]

    How to fix: use a co2_method with period (for co2_max_period) or total (for co2_max_total) in it, or remove the limit.

    W-0104

    One-variable connection at the edge of a non-synchronous group (warning). Console line:

    Warning: one-variable connection crosses a non-synchronous group boundary (<N> cases, e.g. '<name>') [W-0104]

    The non-synchronous limit counts the flows of a connection with one node in the group both ways: the flow into the group as infeed, the flow out of it as supply. A one-variable connection (no_losses_no_variable_cost, and the lines of a dc_power_flow_with_angles group, which use it internally) can flow both ways at once at no cost, so the optimiser can loosen the limit by up to the line capacity. The case is named as (connection, group). is_DC connections are not reported.

    How to fix: use transfer_method: exact for the connection (a DC power-flow line: check the results for simultaneous flows both ways).

    Reserve ratio without a dynamic reserve method (warning). Console line:

    W-0490

    Value list possibly changed by a spinedb_api bug (warning). Console line:

    Warning: a spinedb_api bug may have changed the value list on <date> (<N> cases, e.g. '<name>') [W-0490]

    The database's own migration history shows a migration session, between 2024-04-29 and 2025-07-07, that may have run with spinedb_api 0.31 to 0.34. Those versions had a bug: adding a member to a value list could overwrite the list's first member, and every default and value that used that member then silently changed with it. The line names the lists to check; the debug log and the run log give the data versions of the session. FlexTool does not know which library the migration used, so this is a possibility, not a finding. The GUI lists a "Please check this database" message for it when it opens the project, with a button to this checklist. The message repeats at every run and every time the GUI opens the database, also after you have checked, until a repair is recorded in the database: only FlexTool's repair tool records one.

    For invest_methods (migration from data version 21 to 22): the list should contain not_allowed. If it is missing, the method parameter default of invest_method (unit, connection, node) and any value that was not_allowed before that date now read cumulative_limits, which since FlexTool 4.4 lets those entities invest and retire without limit.

    How to fix: run the repair tool on the database, in a terminal:

    flextool-repair-value-list "<database>"

    or, with the Python of FlexTool's environment, python -P -m flextool.cli.cmd_repair_value_list "<database>".

    The tool never changes the database itself. It asks about each default and value that may have changed, and writes a repaired copy (<name>_repaired.sqlite next to it) that records the repair; the warning ends when that copy is used in place of the database. If you have a copy of the database from before the upgrade (data version 21 or older), add --archive "<old copy>": the tool then uses it as evidence. The steps (answers file, exit codes, swapping the copy in) are in Repairing a value list.

    If the tool cannot repair the list (it says so), check it by hand (a checklist):

    1. Make a copy of the database and work on the copy.
    2. In the Spine DB editor, open Parameter value list and the named list (invest_methods). Check that it has every member listed in the parameter reference (14 for invest_methods, among them not_allowed and cumulative_limits).
    3. If a member is missing, add it to the list (at the end).
    4. For invest_methods, set the default value of invest_method of unit, connection and node to not_allowed (FlexTool's default).
    5. Filter the parameter values by invest_method = cumulative_limits. For each one, decide whether it was meant: compare with a copy from before the migration date, your Excel input or your notes. An entity that has no cumulative_max_capacity and should not invest should be not_allowed.
    6. Re-run, and compare the investments and retirements with the previous results.
    7. Run the repair tool on the fixed copy to record the repair: the warning stays until one is recorded. If the tool still cannot read the list (it says so again), run it with --checked-by-hand: you confirm that you have checked every item above, and the tool records the repair in a copy without changing any value.

    If you copied data from this database into another one, check that one too.

    W-0572

    Final solve of a Benders solve failed or disagrees (warning). Console line:

    Warning: final solve of benders solve '<solve>' <problem> (<N> cases, e.g. '<name>') [W-0572]

    After a Benders solve, FlexTool solves the whole model once with the Benders investments fixed (the final solve) and writes the solve's results from it. The line says what went wrong:

    • failed: the final solve did not end with an accepted solution (infeasible, unbounded, a time limit, the solver process stopped or was killed, or the whole model did not fit in memory: then the line says out of memory). The run still ends normally, since the Benders result itself is valid. A configuration, licence or internal error in the final solve (an option the solver refuses, a missing solver or licence) is not this warning: it stops the run with an error, as without Benders. When the Benders solve is followed by other solves, it writes its investments and their costs (as with --benders-final-solve off) and the later solves give the dispatch; when it is the last solve, no result table is written.
    • objective outside the Benders bounds: the final solve's objective is not between the lower and upper bound of the Benders solve (the line gives the three values). The results of the final solve are written. The decomposed and the whole model then do not agree on the cost of the same investments.

    The Benders incumbent is a feasible plan of the whole model, so the final solve should always find a solution at most the upper bound. A failure points to numerical trouble (scaling) or to a problem in the decomposition.

    How to fix: out of memory: --benders-final-solve off (FLEXTOOL_BENDERS_FINAL_SOLVE=off) skips the final solve; add a dispatch solve after the Benders solve to get results. Otherwise check the solver log of the final solve and the scaling lines (--debug shows more). Try the solve without decomposition (decomposition = none) on a smaller case; if the two disagree, report it with the debug log.

    Solver outcome

    W-0540

    Optimal within a multiple of the relative tolerances (note). Console line:

    Note: solve '<solve>' optimal by HiGHS at up to <factor>x its relative tolerances<rolls> (<N> cases, e.g. '<name>') [W-0540]

    HiGHS called the solve optimal, although its solution misses some of HiGHS's tolerances (by default 1e-7) also in relative terms, by up to the factor given (HiGHS's own log says Model status is "Optimal" since relative violation of tolerances is no more than X; the note gives that X). After an interior-point solve without crossover (solver = ipm, run_crossover = off) X measures the relative violations, relative to the size of the numbers in each row and column; after simplex or crossover it measures the absolute infeasibilities and the gap between the primal and dual objectives. The factor tells how serious it is: a factor up to about 10 means the flows, storage levels and costs are accurate to about a millionth (1e-6) of their size, which is far below the accuracy of any input data: the results are usable. The duals (prices) are less exact than the primal values: small differences in prices between equivalent nodes or time steps can be numerical noise. The debug log names the checks and their largest violations. Each solve is noted once: for a rolling solve the note comes after its rolls, says in how many rolls it happened and gives the largest factor; the debug log names each roll, the worst first.

    How to fix: usually nothing. If prices or small values matter, or the factor is large: add run_crossover = on to the solve's solver_arguments to run crossover (or set solver = simplex there). Crossover turns the interior point into a vertex solution that HiGHS certifies against the absolute tolerances; it takes extra time, which on a large model can be much more than the interior point itself. Scaling problems (see the Coefficient ranges HiGHS prints and the autoscale line) make the outcome more likely: fixing the units of very large or very small numbers helps too.

    W-0541

    Interior point without crossover: HiGHS's tolerance warnings (note). Console line:

    Note: these HiGHS IPX warnings ('imprecise', 'Unwelcome IPX status', 'Model status changed from Unknown to Optimal') are expected in this solver mode and the solve was accepted by FlexTool's checks (<N> cases, e.g. '<name>') [W-0541]

    The solve ran the interior-point method without crossover (solver = ipm, run_crossover = off) and HiGHS called the result optimal. Such a solution is an interior point, not a vertex, and HiGHS checks it against its tolerances (by default 1e-7) both in absolute terms and relative to the size of the numbers in each row and column. Its log then often has WARNING lines that read as alarms but are expected here:

    • Status interior point solve: imprecise, WARNING: Unwelcome IPX status ... run_crossover is "off", WARNING: Running postsolve on non-optimal solution of reduced LP and WARNING: Model status changed from "Unknown" to "Optimal": the interior point stopped a little short of HiGHS's own target, and the solution of the full model meets the tolerances after postsolve.
    • WARNING: Solution optimality conditions (also : Before postsolve) with a table of num/max violations: absolute violations in rows or columns with large numbers. The relative numbers in the same table are what counts.
    • WARNING: LP solver claims optimality, but with ... relative ... and Model status is "Optimal" since relative violation of tolerances is no more than X: the relative violations are at most X times the tolerance. A "Before postsolve" one concerns the presolved model only. An X up to about 10 means the flows, storage levels and costs are accurate to about a millionth of their size, far below the accuracy of any input data.

    The results are usable. The duals (prices) are less exact than the primal values: small price differences between equivalent nodes or time steps can be numerical noise.

    The note is printed once per run, at the first interior-point solve without crossover, whether or not HiGHS printed these warnings for it; it covers the warnings of the later solves of the run too. FlexTool cannot read HiGHS's log. A solve that HiGHS accepted only at a multiple of its tolerances also gets W-0540, with that multiple.

    How to fix: usually nothing. If a certified optimum matters: add run_crossover = on to the solve's solver_arguments to run crossover (or set solver = simplex there). Crossover turns the interior point into a vertex solution that HiGHS certifies against the absolute tolerances; it takes extra time, which on a large model can be much more than the interior point itself. Scaling problems (see the Coefficient ranges HiGHS prints and the autoscale line) make the outcome more likely: fixing the units of very large or very small numbers helps too.

    W-0542

    Near-optimal solve accepted (note). Console line:

    Note: solve '<solve>' not certified optimal by HiGHS; its feasible solution is used (<N> cases, e.g. '<name>') [W-0542]

    HiGHS ended the solve with model status Unknown: after an interior-point solve without crossover, postsolve left the dual objective slightly inconsistent, so HiGHS cannot certify the optimum. FlexTool checked the solution itself: the primal solution (the flows, storage levels and investments the results are made of) is feasible within the tolerances, and the gap between the primal and dual objectives is within the accepted optimality gap (FLEXTOOL_ACCEPT_PD_GAP, by default 1 %), so the solution is used as near-optimal. The objective can be off the true optimum by at most that gap. The debug log and the run record (_run_status.json) give the numbers. A solve that fails these checks stops the run with an error instead. Each solve is noted once.

    How to fix: usually nothing. If the exact optimum or the prices matter: add run_crossover = on to the solve's solver_arguments to run crossover (or set solver = simplex there). Crossover turns the interior point into a vertex solution that HiGHS certifies against the absolute tolerances; it takes extra time, which on a large model can be much more than the interior point itself. Scaling problems (see the Coefficient ranges HiGHS prints and the autoscale line) make the outcome more likely: fixing the units of very large or very small numbers helps too.

    W-0500

    Two solves realize the same dispatch (warning). Console line:

    Warning: solves realize the same <steps> time steps (<periods>); the later is kept (<N> cases, e.g. '<name>') [W-0500]

    Both named solves realize dispatch in the same time steps of the named periods. The solve that runs later keeps those time steps; the earlier solve's results for them are not reported. The line counts the time steps and periods over all levels of the two solves (the rolls of a rolling solve count as that solve). This is expected when, for example, a dispatch solve is nested inside an investment solve.

    How to fix: if the overlap is not meant, check the realized_periods of the two solves (and, for rolling solves, rolling_jump / rolling_horizon) so that each time step is realized by one solve.

    W-0501

    Two solves realize the same investment periods (warning). Console line:

    Warning: two solves both realize the investments of <periods> (<N> cases, e.g. '<name>') [W-0501]

    Both named solves list the same period(s) in realized_invest_periods. Investments of a period should be realized by only one solve. If the later solve can also invest in that period, it treats the earlier solve's investment as existing capacity and may invest more on top of it; the reported invested capacity and investment cost of the period then come from the later solve only, although the total capacity includes both.

    How to fix: remove the period from the realized_invest_periods of one of the solves.

    W-0502

    Realised state not before the solve's start (warning). Console line:

    Warning: a realised state ends after solve '<solve>' starts; not carried (<N> cases, e.g. '<name>') [W-0502]

    A solve continues the states (storage levels, on-line units, ramps) that the earlier solves of its nesting level realised before its first time step. The named earlier solve realised a state that ends at or after the start of this solve, so it is not carried into this solve. The debug log gives the time steps.

    How to fix: check the realized_periods and the time steps of the two solves: a solve that continues another should start after the last time step the other realizes.

    W-0503

    First solve of a nesting level does not continue the higher level (warning). Console line:

    Warning: solve '<solve>' starts a level: storage not from the higher level (<N> cases, e.g. '<name>') [W-0503]

    The solve is the first solve of its nesting level, so its storage nodes start from their storage_start_end_method (fix_start) or free, not from the state a solve of a higher level realised before it. This happens when a nesting level first appears later in the model.

    How to fix: usually nothing. If the storage should continue the higher level's state, start the nested level together with the higher level, or give the storage nodes a storage_state_start.

    W-0504

    Minimum up / down time look-back cut short (warning). Console line:

    Warning: minimum <parameter> look-back cut short at a start of solve '<solve>' (<N> cases, e.g. '<name>') [W-0504]

    The process has min_uptime or min_downtime, but at a first time step of a period of the solve the look-back covers 0 hours: the time steps before it belong to an earlier solve, and this step does not continue the last step that solve realized. No realized on-line history reaches it, so the earlier start-ups and shut-downs do not constrain it. The debug log names the time step.

    How to fix: make the solves continue each other in time (a hole or an overlap between the realized time steps of the solves causes this), or accept the looser constraint at that step.

    W-0505

    Group new_stepduration shorter than the solve's time step (warning). Console line:

    Warning: group new_stepduration shorter than the time step of solve '<solve>' (<N> cases, e.g. '<name>') [W-0505]

    The group's new_stepduration would make its nodes coarser than the solve's time step, but it is shorter than that step, so it has no effect: the group's nodes are balanced at the solve's own time step. The debug log gives both durations.

    W-0506

    Rolls of a rolling solve realize the same dispatch (warning). Console line:

    Warning: rolls of solve '<solve>' realize the same <steps> time steps (<periods>); the later is kept (<N> cases, e.g. '<name>') [W-0506]

    Two rolls of the same rolling solve realize dispatch in the same time steps of the named periods. Each roll should realize only the time steps up to the start of the next roll (rolling_jump); here a roll realizes time steps that a later roll realizes again, and the later roll's results are kept. The line counts the time steps and periods over all pairs of rolls; the debug log names each pair and period.

    W-0507

    Unit or connection listed in a coarse group (warning). Console line:

    Warning: unit or connection in a new_stepduration group links nodes outside it (<N> cases, e.g. '<name>') [W-0507]

    The unit or connection (named with the group) is listed in a group that has a new_stepduration longer than the solve's time step, and it connects to node(s) outside that group.     W-0508

    Forecasts where no solve or roll fans out (warning). Console line:

    Warning: stochastic_branches forecasts where no solve or roll fans out; ignored (<N> cases, e.g. '<name>') [W-0508]

    stochastic_branches declares forecasts (a solve, a period and an analysis_time) where no solve or roll fans out, and FlexTool ignores them. A solve or roll fans out once, at its first reveal, and its branches read the forecasts made then through the rest of its horizon. Each case is a complete solve, a period and an analysis time; the debug log gives the forecast branches and the solve or roll whose horizon reaches them.

    How to fix: to use these forecasts, make a roll start there (rolling_solve_jump) or put the later fan in a separate solve; otherwise remove these stochastic_branches rows.

    W-0588

    Realization solve that inherits nothing (note). Console line:

    Note: realization '<solve>' keeps nothing of '<parent>': its results do not depend on it (<N> cases, e.g. '<name>') [W-0588]

    The realization solve takes from its stochastic solve the units online of the units and connections with startup_method linear_fix_in_uc or integer_fix_in_uc, and the investments. Here there are neither: no unit or connection with a _fix_in_uc method has units online in the realization solve (units with linear or integer are decided again with the realized data; units without online variables, or with reduce_unit_detail_method leaving them out, have none), and the stochastic solve decides no investments (no invest_periods or realized_invest_periods; a rolling solve builds no investment in its rolls). Storage and the other states continue from the previous realization, not from the stochastic solve, and reserve is met again with the realized data. So the realized results do not depend on the stochastic solve, and its forecasts only change its own results. The realization of a single solve dispatches its committed window with the realized data and no look-ahead; the realization added to a rolling separate_dispatch solve dispatches each jump with the realized data and then looks ahead with the forecasts made at the end of the jump. Two kinds of rolling solve keep a realization solve that does not look ahead with the forecasts: in a model with delayed units (note W-0594) a rolling separate_dispatch or within_solve solve, and a rolling stochastic solve followed by a realization solve you configure yourself (that solve dispatches as you configured it). The note is printed once per realization solve.

    How to fix: nothing, if that is meant. For a commitment made in the stochastic solve that holds in the realization, give those units startup_method integer_fix_in_uc or linear_fix_in_uc. For a rolling solve that should keep nothing of a separate unit-commitment solve, use dispatch_realization_method within_solve: each roll is then one solve (not in a model with delayed units, note W-0594).

    W-0592

    Outage ends a carried obligation (note). Console line:

    Note: an outage ended an obligation carried over from an earlier solve (<N> cases, e.g. '<name>') [W-0592]

    An earlier solve started these units, or left them ramping down. Their minimum up-time, or ramp-down limit, would have kept them running into time steps where they cannot run: their capacity derated by availability there is below the minimum load of the units the obligation keeps online (for the ramp-down limit, the flow their capacity allows there is below what the limit asks for). That solve could not see the outage, because it lay beyond its horizon or only the realized data have it. FlexTool ends the carried obligation at the first such step, and the rest of its minimum up-time is dropped. A realization solve keeps the units online its stochastic solve committed up to such an outage and decides the unit again from the outage on. A solve that sees an outage coming still keeps the minimum up-time: it does not start a unit it cannot keep. The debug log gives the solve and the step of each unit. The note is printed once per run.

    How to fix: nothing, if the outage could not be foreseen. If it was planned, make sure the solve that starts the unit sees it: give it in the stochastic solve's forecasts, or lengthen rolling_solve_horizon.

    W-0593

    Deterministic solve with stochastic branches (warning). Console line:

    Warning: solve '<solve>' has dispatch_realization_method deterministic: forecasts not solved (<N> cases, e.g. '<name>') [W-0593]

    The solve is a dispatch solve with stochastic_branches, and its dispatch_realization_method is deterministic (the default of a dispatch solve since FlexTool 4.7.0; an investment solve, a solve that is not rolling and has invest_periods or realized_invest_periods, does not read the method and always solves its forecasts). It is solved with the data of the realized: yes branch only, as one timeline: each time step reads the realized series that covers it (where several do, the one made nearest to the start of the solve, or of the roll in a rolling solve). The forecasts and the realization solve are ignored. Without a realized: yes branch, or at a time step no realized series covers, the run stops with an error.

    How to fix: set dispatch_realization_method to within_solve or separate_dispatch to solve the forecasts.

    W-0594

    Realization without look-ahead: delayed units (note). Console line:

    Note: solve '<solve>' has delayed units: each jump is realized without look-ahead (<N> cases, e.g. '<name>') [W-0594]

    The solve is a rolling solve with stochastic_branches and dispatch_realization_method within_solve or separate_dispatch, and the model has units with a delay. Such a solve realizes each jump in a realization solve that dispatches it on the realized data, continuing from the previous realization and keeping what it inherits from the roll's stochastic solve (note W-0588): the realization itself does not look past the jump with the forecasts made at its end. The look-ahead is not available with delays: within the roll a delay wraps the last time steps' flows back to its first ones, and the forecasts that follow the jump would all wrap into the same first time steps. The note names the delayed units and is printed once per run.

    How to fix: nothing, if that is meant. For the look-ahead, model the units without delay.

    W-0639

    Investments branch at the first period (warning). Console line:

    Warning: investment solve '<solve>': investments branch at its first period (expert option) (<N> cases, e.g. '<name>') [W-0639]

    The solve is an investment solve with invest_solve_branching_method investments_at_reveal_period, and its forecasts start at its first period. Every forecast then invests and operates on its own from the start, as one deterministic solve per forecast weighted together (the wait-and-see value of the forecasts). No decision is shared, so nothing can be realized: the solve gets no realization dispatch, and the normal results hold no investment or operation of the forecasts. They are written only by the model.output_horizon dump.

    How to fix: nothing, if the wait-and-see value is intended. To decide one investment for every forecast at the first period, set investments_after_reveal_period (or leave the setting out: operations_only); to learn after a first period, start the forecasts at a later period.

    W-0640

    separate_dispatch on an investment solve (warning). Console line:

    Warning: investment solve '<solve>': dispatch_realization_method separate_dispatch ignored (<N> cases, e.g. '<name>') [W-0640]

    The solve is an investment solve (not rolling, with invest_periods or realized_invest_periods), and it sets dispatch_realization_method separate_dispatch, which applies to dispatch solves only.     W-0532

    Rolling solve: bind_within_timeblock as bind_within_period (note). Console line:

    In a rolling solve each period is one continuous timeblock, so the storage nodes with storage_binding_method bind_within_timeblock use bind_within_period in this solve.

    How to fix: nothing; set bind_within_period on the nodes to say it explicitly.

    W-0533

    Rolls start inside a period (note). Console line:

    Note: rolls of '<solve>' start inside a period; storage carries on (<N> cases, e.g. '<name>') [W-0533]

    The rolls of the rolling solve start inside a period. Storage nodes with bind_within_period (also bind_within_timeblock) or bind_intraperiod_blocks continue that period from the level the previous roll realised; a roll ends its part at least at that level, and the roll(s) holding the period's end end it at the level it started from.

    How to fix: nothing; this is how a rolling solve binds storage within a period.

    W-0534

    Storage start energy can be used up (an endowment) (warning). Console line:

    Warning: storage ends free in '<solve>'; its storage_state_start energy is usable (<N> cases, e.g. '<name>') [W-0534]

    The storage nodes start the solve at storage_state_start on capacity the solve cannot change (existing capacity, no investment or life extension in the start period) and chain forward to a free end: bind_forward_only, no fix_end, no use_reference_value and no end fixed by an upper-level solve. The run may then use this start energy without producing it. This is a valid model of an initial stock (an endowment). The warning is given in the first solve of each level (a start carried from an earlier solve is not an endowment). The debug log gives the energy per node and in total (MWh, on the existing capacity before any retirement in the solve).

    How to fix: nothing, if the initial stock is meant. If the storage should return it, use storage_start_end_method fix_start_end, a cyclic storage_binding_method or storage_solve_horizon_method use_reference_value.

    W-0535

    Start of investable storage not matched at the end (warning). Console line:

    Warning: storage start on investable capacity not matched at the end in '<solve>' (<N> cases, e.g. '<name>') [W-0535]

    The storage nodes start the solve at a level the solve decides by investing: storage_state_start (or the reference value of use_reference_value) on capacity the solve can build or extend in the start period, and chain forward. The matching end (the end held at least at the start) needs both ends in one solve, and this solve does not hold the last step of the model, so it is not applied: built storage can deliver its start energy without producing it. A free start (fix_nothing) is not warned about: the later solve that reaches the end of the model matches it.

    How to fix: use storage_binding_method bind_within_solve (or bind_within_solve_blended_weights), or storage_start_end_method fix_start_end with storage_state_end at least storage_state_start.

    W-0536

    Start differs from the reference value (warning). Console line:

    Warning: storage_state_start differs from the reference in '<solve>'; start used (<N> cases, e.g. '<name>') [W-0536]

    The storage nodes have storage_solve_horizon_method use_reference_value and a storage_start_end_method that fixes the start (fix_start or fix_start_end), and their storage_state_start differs from storage_state_reference_value at their first step. The start uses storage_state_start. (A node that does not fix its start starts from the reference value.) The debug log gives both values per node.

    How to fix: give storage_state_start the reference value of the first step, or set storage_start_end_method to fix_nothing (or fix_end) so that the start follows the reference value.

    W-0537

    Storage balance slack bypasses a hard balance (warning). Console line:

    Warning: storage slack in solve '<solve>' can bypass a linked hard balance (<N> cases, e.g. '<name>') [W-0537]

    The storage nodes have balance slack (penalty_method not off) and a unit or a connection links them to node(s) with penalty_method off. The storage slack can supply or absorb energy for those nodes and so bypass their hard balance at the storage node's penalty, which can be far below what an unmet demand there should cost. Only pure storage nodes (no own inflow or demand, e.g. a battery) are named: the slack of a node with its own demand is the intended outlet of that demand. The debug log gives the linked nodes of each storage node.

    How to fix: if the balance should hold, set penalty_method off on the storage node too (or give it a high penalty), so that a shortfall shows where it arises.

    W-0538

    Reference value below the start of investable storage (warning). Console line:

    Warning: reference end below the start in '<solve>'; caps storage investment (<N> cases, e.g. '<name>') [W-0538]

    The storage nodes have storage_solve_horizon_method use_reference_value, their reference value at the end lies below their start, and the solve can invest in their storage in the period they start in. As for fix_start_end, the matching end stays (the end at least at the start), so storage built must still return its start energy, which caps that investment.

    How to fix: give storage_state_reference_value at least the start if the storage should be built freely.

    W-0539

    Plain storage cycle on representative periods (warning). Console line:

    Warning: storage in '<solve>' cycles over representative periods unweighted (<N> cases, e.g. '<name>') [W-0539]

    The solve is on representative periods (its timesets have representative_period_weights), and the storage nodes use a storage_binding_method (bind_within_solve, bind_within_period or bind_intraperiod_blocks) that moves the storage level from one representative period to the next without their weights, while the flows of each step count with the weight of its period. This is reasonable when the representative periods have equal weights or when the timing of the storage's inflows does not matter (e.g. pumped hydro, large heat storage). Nodes with storage_start_end_method fix_start_end are not named (their binding method is not used). The debug log gives the timesets and the method of each node.

    How to fix: if the weights matter, use the *_blended_weights method, which weights the transfer: bind_within_solve -> bind_within_solve_blended_weights, bind_within_period and bind_intraperiod_blocks -> bind_within_period_blended_weights.

    Warning: flowGroup's flows are at nodes with different units of measure (<N> cases, e.g. '<name>') [W-0108]

    The flows of the flowGroup are at nodes with different unit_of_measure values, so its sums are labelled Mixed units of measure!. The debug log lists the nodes by unit.

    How to fix: keep flows of one quantity in a flowGroup, or accept the mixed label.

    W-0221

    Connection between nodes in different units of measure (warning). Console line:

    Warning: connection joins nodes with different units of measure (<N> cases, e.g. '<name>') [W-0221]

    The two nodes of the connection have different unit_of_measure values. Its flow, losses and capacity are labelled Mixed units of measure!; a connection moves one quantity. The debug log lists the nodes by unit.

    How to fix: check that this is intended (a unit converts between quantities).

    W-0305

    unit_of_measure that names a rate (warning). Console line:

    Warning: node's unit_of_measure looks like a rate, not an amount (<N> cases, e.g. '<name>') [W-0305]

    unit_of_measure is the amount unit (m3, MWh), not the rate (m3/h, MW); with a rate the flows would be labelled wrong. The debug log suggests the amount unit.

    How to fix: set the amount unit (e.g. m3 for m3/h).

    W-0401

    Commodity of nodes in different units of measure (warning). Console line:

    Warning: commodity is used by nodes with different units of measure (<N> cases, e.g. '<name>') [W-0401]

    The commodity__node nodes of the commodity have different unit_of_measure values. Its price and co2_content are per the unit of each node, so one value cannot fit them all. The debug log lists the nodes by unit.

    How to fix: use one commodity per unit of measure.

    User constraints

    W-0004

    User constraint without variables in a solve (warning). Console line:

    Warning: user constraint has no variable in solve '<solve>'; left out (<N> cases, e.g. '<name>') [W-0004]

    Every coefficient of the user constraint refers to something the solve does not have (for example the invested capacity of a unit that cannot invest in this solve, or a flow outside the solve's periods), so each of its rows reads constant sense constant. Those rows always hold, so the constraint is left out of the solve. (Rows that cannot hold, such as 0 >= 600, stop the run with an error instead.) Each constraint is named once per run; the debug log gives the rows per period.

    How to fix: usually nothing: the constraint is meant for other solves. If it should bind in this solve, give it a coefficient on something the solve has (check the entities' invest_method, the solve's periods and the constraint's sense / constant).

    Warm start and memory

    W-0550

    Warm-start basis not used (warning). Console line:

    Warning: warm-start basis not <step> for solve '<solve>'; <effect> (<N> cases, e.g. '<name>') [W-0550]

    The run has warm start on (--warm-start / FLEXTOOL_WARM_START=1), and FlexTool could not use the cached HiGHS basis of the solve: either loading the basis into the solve failed (not loaded: the solve ran from scratch) or saving the basis of the finished solve failed (not saved: a later solve of the same model, in this run or a later one sharing the basis cache, starts without it). The results are not affected; only the solve time can be longer. The rolls of a rolling solve share one line; the debug log has the error of each.

    How to fix: usually nothing. If it happens in every run, check that the basis cache folder (--basis-cache-dir, by default <work folder>/basis_cache) is writable and its files are not damaged (deleting the folder is safe), and report it with the debug log (--debug).

    W-0551

    Save-memory mode (note). Console line:

    Note: save-memory mode: every solve is rebuilt and solved by HiGHS in a separate process (<N> cases, e.g. '<name>') [W-0551]

    The run has --save-memory / FLEXTOOL_SAVE_MEMORY=1 on. Each solve then builds its LP from scratch, writes it to an MPS file and lets HiGHS solve it in a separate process, so the memory HiGHS needs while solving is not added to this process's memory. An LP is not reused between solves (warm reuse is off), and each solve takes some tens of seconds more for the file I/O. The note is printed once per run.

    How to fix: nothing, if the mode was meant (for models that run out of memory otherwise). For faster solves when memory is enough, run without --save-memory and unset FLEXTOOL_SAVE_MEMORY.

    W-0552

    No warm start for this solver (note). Console line:

    Note: warm start is not available for solver '<solver>'; every solve is built from scratch (<N> cases, e.g. '<name>') [W-0552]

    Reusing the LP of an earlier solve (and the warm-start basis cache) works with HiGHS only. With another solver every solve builds its LP from scratch, so a run with many solves (for example the rolls of a rolling solve) takes longer than with HiGHS. The results are not affected. The note is printed once per run.

    How to fix: nothing, if the solver was meant. For warm reuse, use HiGHS (the solve's solver).

    W-0553

    Warm reuse off (note). Console line:

    Note: warm reuse is off (warm=False); HiGHS solves run in a separate process (<N> cases, e.g. '<name>') [W-0553]

    The run was started with warm=False (run_chain_from_db / run_orchestration used from Python), so no LP is reused between solves. Each HiGHS solve then builds its LP from scratch, writes it to an MPS file and is solved by HiGHS in a separate process (as in save-memory mode), which keeps the memory of this process low. Each solve takes some tens of seconds more for the file I/O. The results are not affected. The note is printed once per run.

    How to fix: nothing, if it was meant. For faster solves, leave warm at its default (True).
